# 02. 개발 정책 — 코딩 규칙 / TDD / 커밋 / 안정 ID

## 1. 안정 ID(Stable ID) 규칙 — 최우선 규칙

**모든 요구사항은 안정 ID(FR-XXX)를 가지며, 그 ID는
requirements → design → tasks → code(docstring) → test(함수명)까지 관통한다.**

- 형식: `FR-001`, `FR-002` … (기능 요구사항) / `NFR-001` … (비기능 요구사항)
- **한 번 부여한 ID는 절대 재사용·재번호 부여하지 않는다.** 요구사항이 폐기되면
  번호를 비우지 말고 `FR-007 (폐기, 사유: ...)` 로 남긴다.
- 요구사항이 쪼개지면 하위 ID를 만든다: `FR-003` → `FR-003a`, `FR-003b`
  (원본 ID는 상위 개념으로 유지해 추적선이 끊기지 않게 한다.)

### 관통 방식 (각 계층에서의 표기)

| 계층 | 경로 | 표기 방법 |
|---|---|---|
| requirements | `aidlc-docs/inception/requirements/requirements.md` | 각 요구사항 제목에 `FR-XXX` |
| design | `aidlc-docs/**/functional-design/*.md` 등 | 설계 항목마다 `구현: FR-XXX` 명시 |
| tasks | `aidlc-docs/**/plans/*.md` | 체크박스 항목마다 `(FR-XXX)` |
| code | 소스 파일 | 함수/클래스 docstring 첫 줄에 `FR-XXX:` |
| test | 테스트 파일 | 테스트 함수명에 포함: `test_FR_003_...` |

### 검증

- 어떤 `FR-XXX` 든 위 5개 계층 전부에서 grep으로 찾을 수 있어야 한다.
- 구현·테스트가 없는 요구사항, 요구사항이 없는 코드는 **모두 결함**으로 본다.
- 각 단계 완료 시 누락된 ID가 있으면 `aidlc-docs/audit.md` 에 기록하고 보완한 뒤 넘어간다.

## 2. TDD 정책

- 순서: 실패하는 테스트 작성 → 최소 구현 → 리팩터링. 구현 코드보다 테스트를 먼저 쓴다.
- 테스트 없는 기능 코드는 머지하지 않는다.
- 테스트 계층과 목표: TODO (예: 단위 / 통합 / E2E 각각의 범위와 커버리지 기준)
- 외부 의존(AWS·모델 API)은 TODO (모킹 방침, 계약 테스트 여부)
- 테스트 함수명 규칙: `test_FR_003_주문_생성시_재고가_차감된다` 처럼
  **안정 ID + 한글/영문 서술**로 무엇을 보장하는지 읽히게 쓴다.

## 3. 코딩 규칙

- 네이밍: TODO
- 파일·디렉터리 구조: TODO
- 주석 정책: TODO (무엇을이 아니라 왜를 남긴다)
- 에러 처리: TODO (예외를 삼키지 않는다 / 실패 시 로그에 남길 정보)
- 로깅: TODO (레벨 기준, 민감정보 금지 항목)
- 린터·포매터: TODO (CI에서 강제 여부)
- 금지 사항: TODO (예: 비밀값 하드코딩, 사용하지 않는 코드 주석 처리 후 방치)

## 4. 커밋 규칙

- 형식: Conventional Commits — `<type>(<scope>): <subject>`
- type: `feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `ci`
- 본문에 관련 안정 ID를 명시한다: `Refs: FR-003, FR-004`
- 한 커밋은 한 가지 일만 한다. 산출물(`aidlc-docs/`)과 코드 변경은 분리해 커밋한다.
- 커밋 메시지에 "AI가 만들었다" 같은 서술 대신 **무엇이 왜 바뀌었는지**를 쓴다.

## 5. 브랜치 / PR

- 브랜치: TODO (예: `feat/FR-003-order-create`)
- PR 단위: TODO (unit 단위 / 스테이지 단위)
- 리뷰 기준: TODO
- PR 설명에 포함할 것: 관련 `FR-XXX`, 대응 산출물 경로, 테스트 결과

## 6. AI 협업 규칙

- 요구사항이 모호하면 구현 전에 다지선다 역질문을 먼저 받는다. 추측 구현을 허용하지 않는다.
- 각 phase는 사람의 명시적 승인 후 진행한다.
- 승인 시 **판단 근거**를 함께 남긴다. `aidlc-docs/audit.md` 의
  `[사용자 판단·승인 근거]` 필드가 "승인합니다" 한 줄로 채워지면 그 기록은 불완전한 것으로 본다.
